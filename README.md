# ПАК сортировки товаров — Трек 3

Программно-аппаратный комплекс, определяющий категорию товара на подводящем участке
сортировочного центра и физически маршрутизирующий его в одну из трёх зон (B/C/D).
Решение — цифровой двойник на PyBullet: единое ядро (классификатор + конечный автомат)
работает через слой абстракции над двумя взаимозаменяемыми бэкендами — `sim` (PyBullet)
и `rig` (реальный стенд, собирается параллельно, backend пока заглушка с TODO).

## Быстрый старт

```bash
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pytest tests/ -v                                          # 16 юнит-тестов классификатора/K
python run.py --backend sim --scenario typical --headless # полный сценарий, 30 товаров
```

Или в Docker (см. «Ограничения» про сборку образа ниже):

```bash
docker build -t pak-sort .
docker run --rm pak-sort --backend sim --scenario typical --headless
```

GUI-режим (посмотреть сцену вживую, не headless): `python run.py --scenario borderline --gui`.

## Постановка и подход

Товар едет по подающему конвейеру A (500×700 мм, 1 м/с, лента не останавливается) к
накопителю/зоне детекции. Классифицируется в одну из трёх категорий строго по правилам
ТЗ: (1) габариты OBB вне (10×10×2 .. 450×320×320) мм → **C**; (2) иначе K =
r_вписанной/R_описанной > порога → **D**; (3) иначе → **B**. Дальше — физическая
маршрутизация: **B** едет прямо в основной сортировщик (конвейер B, зафиксирован
схемой на +7000/+1500 мм от A), **C** и **D** выталкиваются поперечными шиберами в
свои лотки и ролл-кейджи.

**Механизм исполнительной части — 2 шибера и 3 камеры** (подтверждено реальным
стендом, который команда собирает параллельно), а не рука с присоской: это входит в
разрешённый ТЗ тип механизма («поперечные толкатели / селекторы»). Камера `infeed`
над зоной детекции — для классификации; `gate_c`/`gate_d` над лотками отводов — для
физического подтверждения, что товар действительно там оказался.

### Backend Protocol

```python
class Backend(Protocol):
    def grab_frame(camera) -> Frame        # RGB + depth, БЕЗ маски сегментации
    def reference_frame(camera) -> Frame   # кадр пустой сцены — для фонового вычитания
    def belt_speed() -> float              # ТЕКУЩАЯ скорость (не номинальная — важно для faults)
    def actuate(zone: "C"|"D") -> bool     # блокирует до конца хода шибера, мех. итог
    def home() -> None
```

`core/fsm.py` работает с этим протоколом и не знает, `SimBackend` за ним или
`RigBackend`. FSM на товар: `IDLE → DETECT → CLASSIFY → TRACK → ACTUATE → CONFIRM →
DONE`, ветка `RECOVERY` при срыве хода шибера или неподтверждённой посадке в лоток —
до `max_gate_retries` повторных импульсов, дальше честный `success=False` в лог.
DETECT и CONFIRM используют попиксельное фоновое вычитание (`core/vision.py`)
относительно реального кадра пустой сцены — не угаданную константу.

## Признак «круг в сечении» (core/cross_section.py)

Это не силуэт сверху: лежащий цилиндр сверху выглядит прямоугольником. Меш режется
10-15 плоскостями перпендикулярно каждой из трёх **главных осей инерции** (не мировых
XYZ), для каждого среза берётся наибольший контур с заполненными дырами (важно для
полых моделей — см. «Находки» ниже), R — минимальная описанная окружность
(`trimesh.nsphere`), r — полюс недоступности (`shapely.ops.polylabel`). K = max по всем
срезам и осям. Порог `k_threshold` — параметр конфига (default 0.7 — текстовое значение
ТЗ; иллюстрация в том же документе даёт 0.8 — реальное противоречие, не решаем его за
заказчика, выносим в конфиг/CLI). `scenarios/borderline.yaml` специально показывает,
что это не абстрактная разница: обычный короб 449×300×150 и скруглённый квадрат с
K=0.79 меняют итоговую категорию (B↔D) в зависимости от того, какое значение порога
взять — `python run.py --scenario borderline --k-threshold 0.8`.

## Сценарии

| Сценарий | Что проверяет | Товаров | Успех |
|---|---|---|---|
| `typical` | штатная работа, все 3 категории | 30 | 100% маршрутизация, 100% accuracy |
| `target_scale` | геометрия участка на полном диапазоне размеров ТЗ (до 450×320×320 и 500×500×500) | 12 | 100% / 100% |
| `borderline` | 449/451мм, K=0.79/0.81, шестигранник K≈0.866, поворот 35°, товар на ребре | 7 | 100% / 100% |
| `faults` | остановка ленты, товары вплотную, K впритык к порогу, повторные попытки шибера | 11 | 100% / 100% |
| `throughput` | развёртка темпа подачи (SimPy), поиск точки переполнения накопителя | — | переполнение при ≥4500 шт/ч (накопитель 15 слотов), запас 25% над целью ТЗ 3600 шт/ч |
| `long_run` | 8ч модельного времени на целевой нагрузке 3600 шт/ч (SimPy, ускоренно) | 28 700+ | overflow 0.06%, загрузка шиберов 29%/43% |

Цифры в таблице — реальный вывод `python run.py --scenario <имя> --headless` на момент
сдачи (см. `results/<сценарий>/{results.csv,summary.json}`), не ожидаемые значения.

## Находки и решения по ходу работы (честно, а не «сразу заработало»)

- **STL организаторов не центрированы** в локальном начале координат (CAD-экспорт,
  начало в углу) — компенсировано через `collisionFramePosition`/`visualFramePosition`
  при спавне, иначе товар физически перевешивает и падает с ленты.
- **Часть STL — полые оболочки** (бутылка, короб): срез даёт тонкое кольцо, и если
  считать r внутри самого кольца, K занижается на порядок. Дыры (толщина стенки)
  отбрасываются перед расчётом r/R — важен наружный силуэт, не материал стенки. Баг
  найден на реальном `Бутылка.stl` (K получался 0.09 вместо ожидаемо круглого),
  регрессия закрыта тестом на синтетической полой трубе.
- **Вогнутые/большие меши** (шлем, мешок 5.4 МБ) — оффлайн VHACD (`sim/vhacd_prep.py`,
  кэш по хешу файла), включается только когда реально нужно (мера — глубина
  вогнутости наружного контура, не объём: полые модели дают неверное сравнение по
  объёму). На `Мешок.stl` без VHACD PyBullet ронял процесс сегфолтом при попытке
  построить выпуклую оболочку на лету.
- **Поперечная рецентровка ленты против самого шибера**: чтобы товар не сползал с
  ленты на длинном перегоне (лента корректирует только скорость вдоль оси, поперечный
  снос ничем не сдерживался), добавили мягкую рецентровку — но она начала тянуть
  товар обратно к центру ПРОТИВ хода шибера, из-за чего первая попытка выталкивания
  систематически не дотягивала до цели. Рецентровка отключается на время хода шибера.
- **Камера подтверждения не покрывала весь лоток**: лоток намеренно большой (запас на
  снос товара лентой во время хода шибера), а поле зрения камеры не расширили вместе
  с ним — размер/высота камеры теперь считаются из фактической геометрии лотка.

## Известные ограничения

- **Одна камера сверху не может восстановить K из реального RGB-D** — лежащий
  цилиндр и так выглядит сверху прямоугольником, для полноценного профиля нужен
  второй ракурс или структурированный скан. `core/classifier.py` получает эталонный
  меш напрямую (алгоритм K валидирован юнит-тестами и на реальных STL); честная
  часть контура на RGB+depth без ground truth — это DETECT/CONFIRM
  (`core/vision.py`, фоновое вычитание, без сегментационной маски).
- **Тонкие круглые тела** (реальные `plate.stl`, `cylinder.stl`) после толчка шибером
  иногда укатываются/докручиваются за пределы зоны обзора камеры подтверждения —
  честно логируется `success=False`, не скрыто.
- **`Мешок.stl`** не загружается визуальным рендерером PyBullet (`tinyRendererPlugin`)
  даже после VHACD для коллизии — известное ограничение движка на этом конкретном
  файле, не наша логика.
- **Переход A→B** (конец линии A к началу конвейера B, физически смещённому на
  +7000/+1500 мм) — по ТЗ способ передачи на усмотрение команды; в текущей версии
  конвейер B стоит на геометрически верном месте, но отдельный механизм стыковки не
  смоделирован (категория B считается успешной логически, без физического
  подтверждения камерой — в отличие от C/D, для которых предусмотрены `gate_c`/`gate_d`).
- **Товар `box_400x400x300`** (реальный, широкий и лёгкий за счёт полой геометрии)
  систематически требует одной повторной попытки шибера — реальная механическая
  особенность этой формы/массы, не случайность; RECOVERY обрабатывает штатно.
- Минимальный товар по ТЗ (2 мм) и высокая скорость шибера — тот же эффект
  туннелирования, что и лента на 1 м/с при шаге 1/240 с: для очень тонких объектов
  нужен более мелкий шаг физики или увеличенный collision margin.
- Докер-образ содержит `build-essential`/`cmake` как подстраховку — если у pybullet
  нет готового wheel под целевую платформу сборки, первый `docker build` дольше
  обычного (сборка из исходников), это ожидаемо и не является ошибкой.

## Инструменты и почему

PyBullet (симуляция и физика, включая VHACD), trimesh (геометрия, OBB, сечения),
shapely (2D-полигоны сечений, polylabel), OpenCV headless (кадры/видео), NumPy/SciPy,
SimPy (аналитическая модель пропускной способности), PyYAML (сценарии) — весь список
входит в перечень допустимого ПО организаторов. `tools/compare.py` готов сравнивать
`results.csv` со стенда и с симуляции (валидация цифрового двойника) даже без данных
со стенда — прогнан на сравнении двух прогонов симуляции между собой для проверки
самого скрипта.

## Направления развития

- Второй ракурс камеры (или структурированная подсветка) для честного восстановления
  3D-формы и вычисления K без ground truth меша.
- Реальный механизм стыковки A→B и камера подтверждения для категории B.
- Заполнение `backends/rig_backend.py` после того, как определится протокол связи с
  контроллером стенда (шина шиберов, число и модель камер).
