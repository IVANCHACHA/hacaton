# sorter_pak — Трек 3 «Робозон»: ПАК сортировки товаров (2 камеры + 2 шибера)

Программно-аппаратный комплекс для участка сортировочного центра перед основным сортировщиком:
получает товар из накопителя подающего конвейера A, относит его к одной из трёх категорий
(**B** — подходит для сортировки, **C** — не подходит по габаритам, **D** — не подходит без
доупаковки/«круглый»), и физически направляет его в нужную зону. Полная постановка — в
[`тз/`](тз/), вопросы-ответы организаторов — в
[`тз/Задача 3 Робозон _ Вопросы-ответы.md`](тз/Задача%203%20Робозон%20_%20Вопросы-ответы.md).

**Главный документ решения — [`docs/REPORT.md`](docs/REPORT.md)**: подход к классификации,
проектные материалы исполнительной части, результаты симуляции, допущения (со ссылками на
конкретные вопросы-ответы), самооценка по шкале УГТ.

## Архитектура в двух словах

Классификация в постановке — двухступенчатая проверка (сначала габарит, потом «круг в
сечении»). Наше решение зеркалит это один-в-один двумя физическими узлами:

```
конвейер A (фикс., 1 м/с)   зона сенсоров      шибер 1 → C          шибер 2 → D           инфид B
──────────────────────────┬───────────┬─────────────────────┬─────────────────────────►
   0 ─────────────── 2.1 м │   2.4 м   │       3.4 м                  4.4 м        5.6 м
                           │  камера   │   не подходит по         круглое сечение
                           │  сверху + │      габаритам           (K ≥ 0.8 хотя бы
                           │  лазерный │                            в 1 из 3 проекций)
                           │  профиль- │
                           │  ометр    │
```

- **2 сенсора** = камера сверху (footprint + оценка разворота) + поперечный лазерный/ToF
  профилометр (высота + 2-я проекция), см. [`docs/REPORT.md#3-3`](docs/REPORT.md).
- **2 шибера** = по одному на каждую ступень проверки; всё, что прошло обе — едет по прямой в B.
- Накопитель-с-остановкой не требуется (явно допустимо, Q&A #57) — маршрутизация идёт «на лету»
  при постоянной скорости ленты.

Подтверждённые результаты симуляции (300 с, см. [`docs/REPORT.md`](docs/REPORT.md#5) для деталей):
**5148 шт/ч**, **100%** точность маршрутизации, **0** опасных попаданий круглых/негабаритных
товаров в зону B.

## Быстрый старт

Четыре независимых способа посмотреть решение в работе — от самого простого к самому «настоящему».

### 1. Браузер (0 зависимостей, 10 секунд)

```bash
open sim_web/index.html   # или просто открыть файл в любом браузере
```
Живая 2D-анимация участка с реальными габаритами/K из переданных STL, панель метрик и журнал событий.

### 2. Standalone Python (без ROS2)

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install numpy scipy trimesh fast_simplification matplotlib

python3 tools/classify_stl.py          # таблица классификации + сверка с Q&A #113
python3 tools/simulate.py              # метрики (sim_output/sim_metrics_run.json) + GIF-анимация
python3 tools/simulate.py --duration 600 --no-animation   # только метрики, длиннее прогон
```

### 3. ROS2 (целевая архитектура)

Требуется ROS2 (Humble/Jazzy) и `colcon`. **Важно: собирать с `--symlink-install`**, иначе
установленные узлы не найдут `тз/Stl` и `sim_output/` относительно исходников (см.
`core/stl_dataset.py`, `DEFAULT_STL_DIR`/`DEFAULT_CATALOG_PATH`).

```bash
pip install numpy scipy trimesh fast_simplification    # зависимости алгоритмической части
cd /Users/ivan/ros2_ws_2
colcon build --symlink-install --packages-select sorter_pak
source install/setup.bash

ros2 launch sorter_pak sim_launch.py
# в другом терминале:
ros2 topic echo /pak/routing_result
ros2 topic echo /pak/classification
```

Три узла: `conveyor_sim_node` (условная «физика» — лента, сенсоры, приёмники команд шиберов —
заменяется на реальные драйверы камер/приводов без изменений в остальных узлах),
`perception_node` (классификация), `executive_node` (управление 2 шиберами). Подробности сигналов
и топиков — [`docs/REPORT.md`, раздел 4.4](docs/REPORT.md).

> ROS2-узлы разработаны и статически проверены (`python3 -m py_compile`), но не запускались
> вживую в этой среде разработки — ROS2 здесь не установлен. Это явно зафиксировано как
> ограничение в отчёте, а не скрыто.

### 4. ROS2 + Gazebo Harmonic (реальная физика + реальные камеры)

`executive_node` без изменений, `perception_node` дополнен вторым путём: лента/товары/шиберы —
настоящие твёрдые тела в Gazebo, а классификация считается из **настоящих depth-камер** (2 шт.,
рендер + пиксельная обработка через `core/vision.py`), а не подсматривается из ground truth.
Модели товаров сгенерированы из реальных STL организаторов, окрашены по типу (не по категории —
иначе камера могла бы «жульничать»). Подробная инструкция, включая раздел калибровки камер и
таблицу диагностики типичных проблем — **[`docs/GAZEBO.md`](docs/GAZEBO.md)**.

```bash
python3 tools/export_gz_models.py     # тз/Stl -> src/sorter_pak/models/ (уже сделано, но можно перегенерировать)
colcon build --symlink-install --packages-select sorter_pak
source install/setup.bash
ros2 launch sorter_pak gz_launch.py
```

> Протестировано вживую (удалённо, по SSH) на референсной VM — полный цикл спаун → движение →
> рендер камер → классификация → срабатывание шиберов → маршрутизация в C/D подтверждён. По пути
> найдено и исправлено 17 реальных багов за живую отладку (несуществующий SDF-параметр
> скорости, ретрай-шторм, потеря имён моделей в мосте поз, вылет товаров с ленты при спауне под
> углом, недоведение шибером до клетки, засветка камеры направляющими рельсами, неверный резолв
> пути к каталогу товаров, вырожденная инерция тонких товаров, затор у точки спавна под нагрузкой)
> — полный разбор в [`docs/GAZEBO.md`](docs/GAZEBO.md). Известное ограничение: на слабом
> безголовом железе без GPU часть срабатываний уходит в безопасный fail-safe (→ D) вместо
> настоящей классификации по камере, и изредка случается нефизичная нестабильность контактного
> решателя при большом числе одновременных коллизий — не баги этой сессии, деградация под
> нагрузкой, подробности там же.

## Как проверить решение (для жюри)

Соответствие разделу постановки «Требования к проверяемости решения»:

| Что проверяется | Где смотреть |
|---|---|
| Как система определяет категорию товара | [`core/geometry.py`](src/sorter_pak/sorter_pak/core/geometry.py) (`classify_reference`) + [`docs/REPORT.md#3`](docs/REPORT.md) |
| Обработка всех 3 категорий | `tools/classify_stl.py` — таблица по всем 11 переданным STL |
| Передача результата классификации в исполнительную часть | `/pak/classification` → `executive_node` (топики) или `conveyor_sim.py::_sensor_capture`→`_try_shiber` (standalone) |
| Реализация перекладки/перенаправления | [`docs/REPORT.md#4`](docs/REPORT.md) — компоновка, механизм шибера, расчёт усилия |
| Работа на тестовом наборе | `tools/classify_stl.py`, `sim_output/item_catalog.json` |
| Временные ограничения (темп ленты, реакция, cycle time) | [`docs/REPORT.md#4-4`](docs/REPORT.md) — бюджет 1.0 с при задержке 40–120 мс |
| Поведение в пограничных/нештатных случаях | [`docs/REPORT.md#3-3`](docs/REPORT.md) (fail-safe → D), [`docs/REPORT.md#4-5`](docs/REPORT.md) (таблица нештатных ситуаций) |

## Допущения

Полный список со ссылками на конкретные пункты Q&A — [`docs/REPORT.md`, раздел 7](docs/REPORT.md).
