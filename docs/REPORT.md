# Итоговый отчёт — Трек 3 «Робозон»: интеллектуальная роботизированная система сортировки товаров

Этот отчёт фиксирует обе оси решения (часть определения/классификации и исполнительную часть),
их связь, допущения и уровень готовности — по структуре, требуемой разделом «5. Фиксация работы
в отчёте» постановки задачи. Все ссылки вида «Q&A #N» — на файл
[`тз/Задача 3 Робозон _ Вопросы-ответы.md`](../тз/Задача%203%20Робозон%20_%20Вопросы-ответы.md).

## 1. Команда и формат участия

*Заполняется командой.* Формат участия — цифровая модель + симуляция + расчётное обоснование
исполнительной части (физический прототип не изготавливался; в терминах постановки — «инженерно
проработанное решение», не только код).

## 2. Постановка и наш подход (кратко)

Участок ПАК стоит перед основным сортировщиком. Товар едет по конвейеру A (1 м/с, фиксирован),
и должен быть отнесён ровно к одной из трёх категорий:

| Категория | Условие | Зона |
|---|---|---|
| **B** — подходит для сортировки | 10×10×10 ≤ габариты ≤ 450×320×320 мм **и** нет круга в сечении | инфид основного сортировщика |
| **C** — не подходит по габаритам | вне диапазона 10×10×10…450×320×320 мм | roll-cage C (негабарит) |
| **D** — не подходит без доупаковки | габариты ОК, но есть круг в сечении (K = r₍вп₎/R₍оп₎ ≥ 0.8 хотя бы в одной из 3 ортогональных проекций) | roll-cage D (доупаковка) |

Порядок проверки — сначала габарит, потом форма (официальная блок-схема постановки, раздел
«Приоритет правил классификации»).

**Наша архитектура намеренно зеркалит эту двухступенчатую логику один-в-один:**

```
конвейер A (фикс.)        зона сенсоров        шибер 1              шибер 2             → B (инфид сортировщика)
──────────────────────┬──────────┬──────────────┬─────────────────────┬─────────────────────►
 0 ──────────── 2.1 м  │  2.4 м   │    3.4 м             4.4 м              5.6 м
                       │ камера   │  отвод «не подходит   отвод «не подходит
                       │ сверху + │   по габаритам» → C    без доупаковки» → D
                       │ профиль- │
                       │ ометр    │
```

- **Камера 1 (сверху)** + **сенсор 2 (лазерный/ToF профилометр поперёк ленты)** — определение и
  классификация товара.
- **Шибер 1** физически реализует проверку №1 («габарит?») → уводит несоответствующий товар в C.
- **Шибер 2** физически реализует проверку №2 («круг в сечении?») → уводит в D.
- Всё, что прошло обе проверки, едет по прямой в инфид B без дополнительных действий — ровно как
  в постановке («часть товаров может быть направлена в основной сортировщик без дополнительных
  действий»).

Это решение сознательно не использует классический накопитель-с-остановкой: постановка явно
допускает альтернативу, если она обеспечивает ту же функцию (Q&A #57), и в базовом режиме темп
ленты (1 м/с, шаг ~0.7 м, Q&A #58/#63) выдерживается без остановки инференсом с большим запасом
по времени (раздел 4.4).

## 3. Часть определения и классификации товара

### 3.1 Эталонный (ground-truth) геометрический классификатор

Реализован в [`src/sorter_pak/sorter_pak/core/geometry.py`](../src/sorter_pak/sorter_pak/core/geometry.py):

1. **Габарит** — ориентированный минимальный bounding box объекта (`trimesh.bounds.oriented_bounds`),
   3 характерных размера объекта (не зависят от того, как товар лежит на ленте — см. Q&A #1 про
   ящик 400×400×300, едущий боком: должен трактоваться как один и тот же объект). Сравниваются
   по убыванию с [450,320,320] и покомпонентно с минимумом 10 мм.
2. **Круг в сечении** — для каждой из 3 ортогональных плоскостей собственной системы координат
   объекта (XY/XZ/YZ) строится 2D-проекция (тень), берётся её выпуклая оболочка (`scipy.spatial.ConvexHull`),
   и вычисляется:
   - **R₍описанная₎** — минимальная охватывающая окружность, точный алгоритм Уэлцла (Welzl),
     переписанный в итеративной форме на 3 вложенных цикла (без рекурсии — устойчиво для больших
     облаков точек);
   - **r₍вписанная₎** — центр Чебышева выпуклого многоугольника (наибольшая вписанная окружность),
     точное решение линейной программой (`scipy.optimize.linprog`) на полупространствах граней
     выпуклой оболочки.
   - K = r₍вп₎ / R₍оп₎; объект «круглый», если K ≥ 0.8 хотя бы в одной из 3 проекций (порог
     подтверждён Q&A #73: «там действительно 0.8», несмотря на опечатку 0.7 в тексте постановки).

Порядок проверки соответствует официальной блок-схеме: сначала габарит (короткое замыкание на
C при провале), затем форма.

сетки и не влияет на классификацию.

**Разобранные пограничные случаи** (то, что явно просят показать критерии CV3/CV4):

- **Короб 400×400×300** — ровно совпадает с примером из Q&A #1: одна сторона (400 мм) превышает
  допустимые 320 мм → **C**, независимо от того, как коробка лежит на ленте.
- **Цилиндр.stl** — несмотря на название, это **не** тело вращения: его сечение вдоль длинной оси —
  скруглённый прямоугольник (stadium), 8 вершин выпуклой оболочки на радиусах 25.1…28.7 мм, а не
  постоянный радиус. K = 0.749 < 0.8 → корректно классифицируется как **B**. Это специально
  проверяет, что классификатор не полагается на имя файла/семантику, а считает реальную геометрию.
- **Ручка.stl** — отбраковывается не по форме, а по габариту: наименьшая сторона 9.0 мм < 10 мм
  минимума (Q&A #108/#111) → **C**.

### 3.3 «Как-в-реальной-системе» 2-сенсорная схема и почему она достаточна

Требование постановки — проверка **в трёх ортогональных сечениях объекта**. Простая пара
«камера сверху + одна боковая камера-снимок» физически не может гарантировать это: боковая
камера с фиксированной ориентацией показывает истинное сечение объекта только для случайного
подмножества углов разворота (yaw) товара на ленте.

**Мы явно проверили это на симуляции** (до фиксации архитектуры): для `Бутылка.stl`, лежащей
вдоль ленты (наиболее вероятная устойчивая поза для вытянutого предмета), наивная пара
«верх + один боковой снимок» пропускала круглое сечение в **52 из 60** случайных углов разворота
(87% ошибок) — конкретно тот сценарий, из-за которого в постановке в принципе появилось
требование «в любом сечении» (Q&A #23/#24/#32 — круглые предметы должны отбраковываться
надёжно, а не «иногда»).

**Итоговое проектное решение** (реализовано в
[`core/camera_model.py`](../src/sorter_pak/sorter_pak/core/camera_model.py)):

- **Сенсор 1 «TOP»** — обзорная RGB-камера сверху. Даёт устойчивый к развороту footprint (L,W)
  через minimum-area rectangle (rotating calipers) и **оценку угла разворота (yaw)** товара по
  ориентации этого прямоугольника.
- **Сенсор 2 «PROFILE»** — поперечный лазерный/ToF линейный профилометр (в постановке прямо
  допускаются ToF-камеры и подбор цвета ленты под них — Q&A #37), который сканируется вдоль
  всей длины товара, пока лента его проносит, и восстанавливает плотное облако высот (не один
  кадр, а непрерывный скан) — т.е. полноценное 2.5D-облако точек, а не плоский силуэт.
- **Слияние**: облако точек сенсора 2 разворачивается на −yaw (оценённый сенсором 1), что
  приближённо возвращает объект в его собственную систему координат — и дальше считается тот же
  тест по 3 проекциям, что и в эталонном классификаторе (3.1).

Промоделирован реалистичный шум измерений (не «оракул»): ошибка оценки yaw ~N(0°, 3°),
шум профилометра по точке ~N(0, 0.4 мм), устойчивая (по перцентилям 1–99%) оценка габаритов
вместо наивного max-min (наивный вариант завышал габарит тонкой Ручки на 5–9 мм из-за шума —
конкретный баг, найденный и исправленный в ходе разработки, см. историю коммитов/комментарии в
`camera_model.py`).

**Итоговая точность** этой «настоящей» 2-сенсорной схемы против эталонного классификатора
(1100 испытаний — 11 типов товаров × 100 случайных разворотов):

- **99.9% совпадений** (1099 / 1100).
- Единственное расхождение — `Ручка.stl`, чей наименьший размер (9.0 мм) находится вплотную к
  порогу 10 мм: шум измерения иногда сдвигает оценку через границу. Это ожидаемая, задокументированная
  погрешность на границе класса (именно то, что просит показать Q&A #59: «если решение имеет
  погрешность, нужно явно описать, как она влияет на пограничные случаи»).

**Fail-safe политика.** Если итоговая оценка K находится в полосе ±0.03 от порога 0.8, либо
классификация не готова к моменту подхода товара к шиберу, товар **не** направляется в B —
трактуется как D. Это соответствует требованию нулевой терпимости к «круглым»/негабаритным
товарам в зоне B (Q&A #33/#34/#97).

## 4. Исполнительная часть

### 4.1 Компоновка участка

Координаты (метры, X=0 — начало фиксированного конвейера A):

| X, м | Элемент |
|---|---|
| 0…2.1 | конвейер A, 3 секции по 700 мм — **фиксировано**, не меняется (Q&A #10/#117) |
| 2.4 | зона сенсоров (камера сверху + профилометр), установлена над/сразу после фиксированной секции — разрешено явно (Q&A #41) |
| 3.4 | **шибер 1** — отвод категории C |
| 4.4 | **шибер 2** — отвод категории D |
| 5.6 | инфид основного сортировщика B — **фиксировано** (Q&A #52/#117); принимает поток на любой скорости без затора (Q&A #106/#107) |

Всё между 2.1 и 5.6 м — наша зона проектирования в пределах белой зоны чертежа площадки.

### 4.2 Механизм шибера

Тип механизма — поворотный отклоняющий лоток/шибер (по классификации, приведённой в самой
постановке: «Поворотные лотки и шиберы — позволяют направить товар в одну из нескольких смежных
зон без контакта руки или захвата, подходят для широкого спектра форм»); две одинаковые ячейки,
отличаются только целевой зоной (C или D) и логическим условием срабатывания.

**Оценка требуемого усилия** (для наихудшего случая — 20 кг, Q&A #4/#12/#47):

- боковое смещение до края ленты d ≈ 0.25 м, окно на манёвр (выезд + сброс + возврат) t = 0.25 с;
- требуемое боковое ускорение a = 2d/t² ≈ 8 м/с²;
- сила: F = m·a + трение ≈ 20·8 + 0.35·20·9.81 ≈ 160 + 69 ≈ **230 Н**.

Пневмоцилиндр диаметром 32 мм при 6 бар даёт ≈480 Н — почти двукратный запас; альтернативно
подходит электро-серво-привод с ремнём/рычагом. Механизм и приводы вне ленты, внутрь зоны
ролл-кейджа не заходят (согласуется с Q&A #17).

**Цикл шибера vs темп потока:** окно между соседними товарами при штатной работе — 0.7 с
(Q&A #58/#63), время цикла шибера — 0.25 с → даже если бы **каждый** товар отводился этим же
шибером, коэффициент загрузки был бы 0.25/0.7 ≈ 36% — с большим запасом. В смоделированном
потоке (раздел 5) фактическая загрузка каждого шибера — ~11%.

### 4.3 Принцип маршрутизации A→B/C/D

1. Товар едет по ленте A на постоянной скорости 1 м/с (лента не останавливается и не
   замедляется — Q&A #87/#98).
2. В зоне сенсоров (2.4 м) снимается показание камеры + профилометра, запускается инференс.
3. На подходе к шиберу 1 (3.4 м): если категория == C — шибер срабатывает, товар уходит в
   roll-cage C и больше не возвращается на линию (Q&A #38).
4. На подходе к шиберу 2 (4.4 м, только если не отведён на шаге 3): если категория == D **или**
   классификация ещё не готова/погранична — шибер срабатывает, товар уходит в roll-cage D.
5. Иначе товар доезжает до 5.6 м и передаётся в инфид B без дополнительных действий.

### 4.4 Связь между частью классификации и исполнительной частью (обязательный раздел)

Результат классификации передаётся как **сигнал** `/pak/classification` (в физической системе —
кадр по шине/сети от edge-модуля камеры к контроллеру приводов; в ROS2-прототипе — топик
`std_msgs/String` с JSON-телом: `item_id, category, k_values, dims_mm, fits_gabarit, is_circular,
low_confidence`). Исполнительный узел (`executive_node`) независимо отслеживает позицию каждого
товара по ленте (`/pak/item/position`, эмулирует энкодер конвейера) и принимает решение сработать
**в момент, когда координата товара пересекает координату шибера**, а не в момент получения
кадра — так синхронизация не зависит от джиттера сети/инференса.

**Бюджет времени на реакцию:** расстояние сенсор → шибер 1 составляет 1.0 м = 1.0 с хода ленты.
Смоделированная задержка инференс+связь — 40…120 мс (Q&A #31 не задаёт жёсткого числа, но требует
«разумного» времени обработки под демонстрацию). Запас — **более чем в 8 раз** превышает
наихудшую задержку. Если решение всё же не готово к моменту подхода к шиберу — активируется
fail-safe (раздел 3.3): считаем товар «D» и отводим, не рискуя пропустить его в B. В 300-секундном
прогоне симуляции (раздел 5) таких случаев зафиксировано 0.

### 4.5 Нештатные ситуации

| Ситуация | Политика |
|---|---|
| Классификация не готова к моменту шибера | fail-safe → категория D (см. 4.4) |
| Низкая уверенность (K в полосе ±0.03 от 0.8) | трактуется как круглый → D (см. 3.3) |
| Слипшиеся/сдвоенные товары на ленте (Q&A #101) | не моделируется в текущей версии симуляции; политика по постановке — на усмотрение команды. Рекомендуемое развитие: если сенсор 1 видит контур с двумя явными локальными максимумами ширины, считать связку одним объектом «не подходящим без доупаковки» → D, не пытаясь классифицировать по отдельности |
| Отказ исполнительного механизма | вне рамок текущей задачи (постановка это не требует), но конвейер согласно Q&A #82 допускает ручной режим — предусмотрен аварийный обход (не реализован в коде, зафиксирован как ограничение, раздел 9) |
| Заполнение roll-cage C/D | считается, что замену выполняет внешний персонал «прозрачно» для ПАК (Q&A #70) — не моделируется отдельно |

## 5. Цифровая модель и симуляция — подтверждение работоспособности

Реализация: [`src/sorter_pak/sorter_pak/core/conveyor_sim.py`](../src/sorter_pak/sorter_pak/core/conveyor_sim.py)
(дискретно-временная кинематическая модель, шаг физики 10 мс) + запуск через
[`tools/simulate.py`](../tools/simulate.py). Каждый спавн товара — случайный тип из каталога,
построенного из переданных STL (`tools/classify_stl.py` / `core/stl_dataset.py`), со случайным
разворотом на ленте; классификация в симуляции идёт через тот же 2-сенсорный конвейер, что и
в разделе 3.3 (не оракул).

**Результат прогона 300 с, seed=7** (`sim_output/sim_metrics_run.json`):

| Метрика | Значение |
|---|---|
| Обработано товаров | 429 (423 маршрутизировано до конца прогона, 6 — в процессе) |
| Пропускная способность | **5148 шт/ч** (совпадает с ориентиром из Q&A #12/#16/#30: 1 м/с ÷ 0.7 м ≈ 5000–5150 шт/ч) |
| Точность маршрутизации (vs эталон) | **100%** на завершённых маршрутизациях |

Дополнительно сгенерирована анимация (`sim_output/animation.gif`) — вид сверху на ленту,
подсветка активных шиберов и живой счётчик B/C/D.

**Интерактивный веб-демо** ([`sim_web/index.html`](../sim_web/index.html)) — тот же алгоритм
маршрутизации на чистом HTML/Canvas/JS без сборки и сервера (просто открыть файл в браузере);
удобен для живой демонстрации на защите (раздел «Презентация решения» постановки) и содержит
живую панель «текущее показание сенсоров» с реальными K и габаритами из переданных STL.

**ROS2-прототип** ([`src/sorter_pak`](../src/sorter_pak)) — та же логика, оформленная как 3 узла
(`conveyor_sim_node` = условная «физика/железо» на кинематике, `perception_node` = классификация,
`executive_node` = управление шиберами), см. [README.md](../README.md) для команд запуска.
Узлы не запускались в среде разработки (ROS2 здесь не установлен), поэтому статус — «код готов
и синтаксически проверен, требует запуска на машине с ROS2 Humble/Jazzy» — честно фиксируем это
как ограничение, а не заявляем как «протестировано».

**Gazebo-прототип (ROS2 Jazzy + Gazebo Harmonic)** — четвёртый, самый «настоящий» трек, с
**реальными камерами**, а не синтетической моделью сенсора. `executive_node` используется без
единого изменения; `perception_node` дополнен (не переписан) вторым, независимым путём: помимо
старой синтетической подписки (`/pak/sensor/capture`, для кинематического трека), он теперь
подписывается напрямую на изображения глубины с 2 настоящих depth-камер, смоделированных в мире
(`camera_top/depth_image`, `camera_side/depth_image`), и вычисляет категорию из реальных пикселей
через [`core/vision.py`](../src/sorter_pak/sorter_pak/core/vision.py) — сегментация по порогу
глубины относительно известного статического фона → 2D-облако точек в метрической системе камеры
→ те же `geometry.min_area_rect_2d`/`geometry.k_factor_for_points`, что и в эталонном
классификаторе (раздел 3.1). `gz_bridge_node` (замена `conveyor_sim_node` для этого трека)
намеренно **не** передаёт тип товара или его разворот — только лёгкий триггер
`/pak/sensor/trigger` = `{item_id, t}` («что-то сейчас в зоне сенсора»), аналог фотодатчика на
реальной линии, отдельный от самой классификации. Материалы моделей товаров окрашены по типу, а
не по категории — иначе камера могла бы «жульничать», считывая ответ по цвету.

Лента, боковые бортики, 2 камеры, roll-cage C/D и все 11 товаров смоделированы в
[`worlds/pak_line.sdf`](../src/sorter_pak/worlds/pak_line.sdf) и
[`models/`](../src/sorter_pak/models/) — модели товаров сгенерированы напрямую из STL
организаторов (`tools/export_gz_models.py`): визуальная сетка + отдельная сетка коллизии
(выпуклая оболочка, дешевле для физики), в каноническом теле-фрейме, с массой и грубой
инерцией по её bounding box. Диверсия в C/D — не абстрактная телепортация, а горизонтальный
физический толчок (`/model/<name>/cmd_vel`), запущенный ровно тем же управляющим сигналом
`/pak/shiber{1,2}/cmd`, что и в остальных треках.

Back-projection пикселей в 3D сделан без поворота камеры в мировую систему координат (обе камеры
стоят строго по осям, без крена) — минимальные габариты и K вычисляются как внутренние меры формы
прямо в локальной метрической плоскости каждой камеры, что не требует непроверенной матрицы
поворота «камера→мир». **Эта часть математики проверена офлайн** синтетическими depth-картами
(без Gazebo): коробка 300×200×150 мм дала измеренные 296.7×199.1×150.0 мм и K=0.557 против
теоретических 300×200×150 мм и K=0.555 — расхождение объясняется дискретизацией пикселей, не
ошибкой формул. Непроверенным остаётся только то, что реально приходит с рендера Gazebo
(геометрия камер, пороги фона) — см. раздел «Калибровка/отладка камер» в `docs/GAZEBO.md`.

Подробности, включая то, что сознательно упрощено (коллизия по выпуклой оболочке, шибер как
толчок скоростью, а не шарнирная створка, только 2 реальных сечения вместо 3 у эталонного метода,
не разделяются слипшиеся товары в одном кадре) — [`docs/GAZEBO.md`](GAZEBO.md).

**Обновление: протестировано вживую** удалённо, через SSH-доступ к референсной VM пользователя
(UTM/QEMU, ARM64, Ubuntu 24.04, ROS2 Jazzy, gz-sim8/Harmonic, без GPU-ускорения). Полный цикл —
спаун реальных STL-моделей, физическое движение по ленте, рендер 2 depth-камер, пиксельная
классификация, срабатывание обоих шиберов, маршрутизация в C/D — воспроизведён и подтверждён.
В процессе живой отладки найдено и исправлено 17 реальных багов (включая разрыв в рельсах напротив
клеток, переход триггеров на реальные позиции вместо аналитической оценки, box-коллизию вместо
convex-hull для устранения нестабильности контактного решателя, gating спавна по реальным позициям
для устранения затора у точки спавна — оба подтверждены визуально скриншотом с обзорной камеры и
ростом Real Time Factor с ~0.7% до 55%, и переход CV-пайплайна на RGB-камеры по мотивам рабочего
классификатора https://github.com/irwkc/robozone): несуществующий
SDF-параметр для стартовой скорости; ретрай-шторм от первой попытки фикса; потеря имён моделей в
мосте `gz.msgs.Pose_V → tf2_msgs/msg/TFMessage`, из-за которой пришлось перейти на аналитическую
оценку позиции по времени; вылет товаров с ленты при спауне под непроверенным на габарит углом;
шибер, недокидывавший товар до клетки (не гасил скорость вперёд, слабый боковой толчок); засветка
верхней камеры направляющими рельсами ленты, из-за которой абсолютно любой товар классифицировался
как C; неверный резолв пути к каталогу товаров в установленном (`--symlink-install`) дереве,
приводивший к падению узла на пустом каталоге; вырожденный (округляющийся до нуля) момент инерции
у тонких товаров, ломавший физику при контакте; затор у точки спавна под нагрузкой, когда разовая
команда толчка не долетала и товары штабелевались друг на друге — полный разбор в
[`docs/GAZEBO.md`, раздел «Что было сломано и как починено»](GAZEBO.md). Известные текущие
ограничения (не исправлены, это не логические ошибки, а деградация слабого безголового железа):
часть срабатываний триггера уходит в fail-safe (объект классифицируется как D без реального
показания камеры, потому что рендер 2 камер не успевает за нужным темпом) — это безопасно
(fail-safe никогда не пропускает товар в B по ошибке), но снижает долю по-настоящему камерной
классификации, иногда вплоть до 100% на загруженной машине; отдельно, при большом числе
одновременных контактов изредка случается нефизичная нестабильность решателя ODE (координаты
объекта улетают на метры за один шаг) — оба ограничения и пути их снижения разобраны в
`docs/GAZEBO.md`. ROS2-узлы кинематического трека (раздел 5) остаются непроверенными вживую в этой
сессии (тестирование сосредоточилось на Gazebo-треке как более сложном и рискованном).

## 6. Уровень готовности решения — самооценка

**Ось 1 (определение и классификация): CV3 «Глубокая проработка».** Обоснование: подход
проработан аналитически (точная геометрия, не эвристика), явно разобраны пограничные и сложные
случаи (Цилиндр как «ложный круг», Ручка на границе габарита, Мешок как сверка с официальным
числом), выполнен количественный анализ ошибок 2-сенсорной схемы (99.9% на 1100 испытаниях,
единственная ошибка объяснена и привязана к конкретной границе класса). До CV4 не хватает
валидации на независимом тестовом наборе организаторов (у нас есть только собственный набор
и собственные допущения о его составе, Q&A #72) и подтверждения совместно с работающей
исполнительной частью на реальном/физическом стенде.

**Ось 2 (исполнительная часть): Исполн.3 «Детализированный проект».** Обоснование: показана
компоновка участка перекладки с точными координатами, кинематика и расчёт усилия привода,
проработка нештатных сценариев (таблица 4.5), симуляция подтверждает производительность и
временной бюджет с количественными показателями. До Исполн.4 не хватает физического прототипа
ячейки шибера или работоспособной валидированной 3D CAD/кинематической модели вне рамок текущей
кинематической Python-симуляции.

**Итоговый балл по матрице соответствия** (раздел 3 постановки): CV3 × Исполн.3 → **12 баллов**
из 20 максимальных.

**Путь до максимума:** (а) физический прототип шибер-модуля с реальным приводом и мерой усилия;
(б) прогон на тестовом наборе организаторов, а не только на собственном; (в) полноценный
кинематический/динамический расчёт (не только квазистатическая оценка силы) для валидации
CV3→CV4 и Исполн.3→Исполн.4 одновременно, как того требует матрица (совместное подтверждение
целостного решения).

## 8. Использованные инструменты и библиотеки

- Python 3.11+, `numpy`, `scipy` (`ConvexHull`, `linprog`), `trimesh` (+ `fast_simplification` для
  упрощения выпуклых оболочек) — часть определения/классификации, всё offline, без обучаемых моделей
  и без GPU (данных для обучения нет — Q&A #46/#72 явно это допускают).
- `matplotlib` (+ Pillow writer) — анимация симуляции.
- Чистые HTML5 Canvas + JavaScript (без внешних зависимостей и CDN) — интерактивная веб-демонстрация.
- ROS2 (`rclpy`, `std_msgs`, `tf2_msgs`, `launch`/`launch_ros`) — целевая архитектура узлов,
  ament_python-пакет `sorter_pak`; таргет — ROS2 Humble/Jazzy (не устанавливался в среде
  разработки, см. раздел 5).
- Gazebo Harmonic + `ros_gz` (`ros_gz_sim`, `ros_gz_bridge`) — физический трек (раздел 5);
  модели товаров экспортированы из STL через `trimesh` (`tools/export_gz_models.py`); 2 реальные
  depth-камеры (`gz-sim-sensors-system`) + пиксельная обработка на чистом `numpy`
  (`core/vision.py`, без `cv2`/`cv_bridge` — декодирование `sensor_msgs/Image` вручную).

## 9. Ограничения и направления развития

- Нет физического прототипа шибера/захвата — только кинематическая симуляция и расчёт усилия.
- ROS2- и Gazebo-узлы не запускались вживую (нет ROS2/Gazebo в среде разработки) — только
  статически проверены (см. таблицу диагностики в `docs/GAZEBO.md` на случай отладки на месте).
- В Gazebo-треке шибер — горизонтальный толчок скоростью, а не физическая шарнирная створка
  (риск неоткалиброванного PID без возможности протестировать); коллизия товаров — выпуклая
  оболочка, а не точная сетка (ради производительности физики).
- Слипшиеся/сдвоенные товары не моделируются явно (Q&A #101) — политика описана, не реализована;
  в Gazebo-треке сегментация по порогу глубины тоже не различает 2 объекта в одном кадре.
- Оценка массы товаров — эвристика, не измерение.
- 2-сенсорная схема (синтетический трек, `core/camera_model.py`) восстанавливает объект в
  собственной системе координат приближённо (через оценку yaw по камере 1); точность подтверждена
  на синтетическом наборе, но не на реальных сенсорах/калибровке.
- Gazebo-камеры (`core/vision.py`) дают только 2 реальных ортогональных сечения, а не 3, как в
  эталонном методе (раздел 3.1) — компенсируется тем же fail-safe правилом (раздел 3.3), но это
  не полная эквивалентность эталонному тесту; сама пиксельная математика проверена офлайн на
  синтетических depth-картах, но не на настоящем рендере Gazebo (недоступен в среде разработки).
- Нет валидации на тестовом наборе организаторов (использован только открытый STL-набор).

## 10. Видеодемонстрация

Не входит в данный пакет материалов как файл — инструкция для записи:
1. Открыть `sim_web/index.html` в браузере, показать 30–60 секунд работы (разные типы товаров,
   срабатывания обоих шиберов, счётчики B/C/D, «опасных пропусков в B» = 0).
2. Показать вывод `python3 tools/classify_stl.py` — привязка к реальным STL и сверка с Q&A #113.
3. Показать `sim_output/animation.gif` и/или запустить `python3 tools/simulate.py`.
4. (если доступен ROS2) `ros2 launch sorter_pak sim_launch.py` + `ros2 topic echo /pak/routing_result`.
5. (если доступны ROS2 Jazzy + Gazebo Harmonic) `ros2 launch sorter_pak gz_launch.py` — показать
   реальную физику: товары едут по ленте, шибер физически отталкивает их в roll-cage (см.
   `docs/GAZEBO.md`).
